# 01 · 为什么并行？

只有有效计算足以覆盖协调成本，并行执行才可能带来收益。这一章先建立成本模型，再用笔记本能够承受的真实任务检验模型。

## 学习目标与前置知识

学完后，你应能区分总工作量、关键路径、任务数和执行槽位，解释增加分区为何可能更慢，并在比较速度前定义正确性。只需要循环、函数、整数运算与计时知识；不要求 Spark 经验。不熟悉 Python 环境或 JDK 时，先阅读复现页。

## 工作量不等于耗时

设总有效工作量为 W，同时执行任务的槽位数为 P，即使分配完全均匀，纯计算耗时也不能低于 W/P。依赖关系还形成关键路径 D，因此 T ≥ max(W/P, D)。调度、序列化、数据传输、倾斜和重试会增加耗时；这个式子是下界，不是性能预测器。

例如八个互不依赖、各耗时 100 ms 的任务，总工作量为 800 ms。两个槽位至少需要四轮，即 400 ms。八个任务不代表八颗 CPU。若前面还有 200 ms 的串行准备，端到端延迟也必须包括它。吞吐量是单位时间完成的工作，延迟是单次工作的等待时长。增大批次可能提高吞吐，同时增加延迟。

固定规模问题中，若不可并行的比例是 s，理想 Amdahl 加速比上限是 1/(s+(1-s)/P)。它假设总工作不变，也忽略协调开销。下面的计算器额外加入每任务开销，帮助检查假设；它没有执行 Spark。

## 对应到 Spark

分区是数据的一份。Stage 为需要计算的分区调度 Task。本实验的 local master 只有两条执行线程；分区增加会带来更多调度轮次。Python Worker、JVM 和操作系统共享一台物理主机。官方指南介绍 Driver 和分布式集合抽象，本实验运行其本地实现。[Spark RDD 指南](https://spark.apache.org/docs/3.5.8/rdd-programming-guide.html)

实验在 240,000 个整数上计算 `(i*31)%997` 的总和，比较 1、8、64 个分区。每种方案都必须等于独立 Python 计算的和；数据量与算术保持不变。工作本身刻意很轻，因此调度和 Python 边界成本可能占主导。它不能证明单分区普遍更好。

```python
rdd = sc.parallelize(range(rows), partitions)
actual = rdd.map(lambda i: (i * 31) % 997).sum()
expected = sum((i * 31) % 997 for i in range(rows))
assert actual == expected
```

## 自测

? 十六个分区、两个槽位，十六个任务能同时运行吗？

! 不能。在没有重试、资源变化的前提下，同时最多运行两个任务，至少需要八轮。

? 这台机器上快了两倍，是否意味着两台机器吞吐也翻倍？

! 不意味着。跨机器会引入网络、存储位置、故障与不同的资源竞争。扩展性实验必须控制负载、改变机器数，并说明总工作量是否固定。
